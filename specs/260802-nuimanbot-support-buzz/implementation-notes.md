# Implementation Notes: NuimanBot Support for Buzz

**Feature:** nuimanbot-support-buzz
**Created:** 2026-08-02

## Purpose

Records decisions made during implementation, edge cases encountered, and deviations from plan.md/tasks.md as they happen. Update this file continuously during implementation — it is the durable record of "why we did it this way" once the spec is archived.

## Technical Decisions

- **P0.1 (2026-08-02):** Chose `github.com/btcsuite/btcd/btcec/v2` + `.../btcec/v2/schnorr` for secp256k1 key generation and BIP-340 Schnorr sign/verify, hand-rolling the NIP-01 event/relay layer in `internal/infrastructure/nostr/`. Rejected `github.com/nbd-wtf/go-nostr` — confirmed archived/maintenance-mode as of Jan 2026 via its own README, recommending an unversioned `@master` successor unsuitable for pinning. Full rationale and sources in research.md Q1.
- **P0.2 (2026-08-02):** Verified directly against `github.com/block/buzz` main branch (not secondary sources): channel messages are Nostr `kind:9` (`KIND_STREAM_MESSAGE`, NIP-29 group chat), channel ID rides in an `h` tag (`#h <channel-uuid>`, required — messages without it are rejected by the relay). There is **no per-message agent-identity tag**; Buzz determines agent/bot status via NIP-29 channel membership role (`MemberRole::Bot`, set through `kind:9000` admin events) and/or a separate per-pubkey `kind:10100` (`KIND_AGENT_PROFILE`) event — both are membership/profile-state lookups, not something derivable from a single `kind:9` message. Full rationale and sources in research.md Q5.
- **`sender_is_agent` scoping for Phase 1 (P1.7):** since accurate agent detection requires NIP-29 membership tracking or a kind:10100 profile lookup — neither of which is built by any Phase 1 task (P1.1–P1.4 only build the kind:9 event/verify/subscription/client path) — `sender_is_agent` is populated as a best-effort `false` for all Phase 1 messages. This is called out explicitly for Phase 2 (P2.3 loop-prevention guard, out of this agent's scope) so its implementer doesn't assume the flag is already accurate.
- **User repository gap discovered during P1.8 wiring:** `usecase/user.Service` requires an `ExtendedUserRepository` (`domain.UserRepository` + `ListAll`/`Delete`), but no production implementation of that interface exists anywhere in the codebase — only a test mock (`internal/usecase/user/service_test.go`). `internal/adapter/gateway/cli/admin_commands.go`'s `AdminCommandHandler` (which also depends on `user.Service`) is itself never constructed/wired in `main.go` today — this whole slice was already dead code before Buzz. To make FR-006/P1.8 real (not just theoretically wired), added a small file-based repository, `internal/infrastructure/storage/file_user_repository.go`, implementing `user.ExtendedUserRepository`, and wired `user.NewService(...)` into `main.go` alongside the Buzz gateway construction. This is new infrastructure-layer code implementing an existing usecase-layer interface — consistent with Clean Architecture (outer layers implement inner-layer-defined interfaces) — not new usecase-layer logic. Not explicitly called out as its own task in tasks.md, but required for P1.8/P1.9 to be more than a stub.

- **P2.2 schema spike (2026-08-02) — `kind:10100`'s doc comment does not match its actual, relay-enforced content schema.** Before writing P2.2's Red step, per tasks.md's required pre-requisite, fetched and read directly (via `gh api`, not secondary sources): `crates/buzz-core/src/kind.rs` (the `KIND_AGENT_PROFILE = 10100` constant and its doc comment, "Agent metadata + owner reference (replaceable, agent-authored)"), `crates/buzz-relay/src/handlers/side_effects.rs` (`handle_agent_profile`, the actual post-storage handler for kind:10100 events), `crates/buzz-cli/src/commands/channels.rs` (`cmd_set_add_policy`, the one CLI command that constructs a kind:10100 event), and `NOSTR.md`.

  **Finding: the doc comment is aspirational/stale. The only field the relay's own code actually parses, validates, or acts on is `channel_add_policy`** (enum `"anyone"|"owner_only"|"nobody"`), a per-pubkey setting controlling who may add that pubkey to a new channel (`NOSTR.md`: "Open: any user, subject to target's `channel_add_policy` (`owner_only`/`nobody` can block)"). `handle_agent_profile` (`side_effects.rs`) does `serde_json::from_str(&event.content)`, reads `content.get("channel_add_policy")`, and returns an error (`"kind:10100 missing channel_add_policy field"`) if it's absent — there is no code path anywhere in the relay that reads or stores an "agent metadata" or "owner reference" field from a kind:10100 event. The one CLI constructor of this kind (`cmd_set_add_policy`) sends `content = {"channel_add_policy": policy}` with no tags. Real agent-identity/persona data (system prompt, model, display name) lives in entirely different kinds — `KIND_PERSONA = 30175` and `KIND_MANAGED_AGENT = 30177` — which are out of scope here.

  **Consequence for this implementation:** `Gateway.publishAgentProfile` (`internal/adapter/gateway/buzz/gateway.go`) publishes the *real*, verified schema — `{"channel_add_policy": "owner_only"}` (constant `buzzChannelAddPolicy`) — rather than fabricating non-existent "identity" fields the relay doesn't read and no other Buzz client would look for. `"owner_only"` was chosen as a conservative default (only the Buzz workspace owner can add this agent to new channels); it is not currently exposed as a `BuzzConfig` field (kept in scope — adding operator-configurability is a natural, separate follow-up if needed, not required by any FR in this spec).

  **This does not affect P2.3's *consumption* side.** research.md Q5/Q2 already resolved, independently of the content schema, that a pubkey publishing *any* kind:10100 event is Buzz's agent-authored signal (per `kind.rs`'s doc comment framing and the type's `is_side_effect_kind`/relay handling, which treats it as a distinct, agent-scoped event kind regardless of its content details) — P2.3's cache-update logic (`handleAgentStatusEvent`) treats the mere *presence* of a kind:10100 event for a pubkey as sufficient to mark it an agent, independent of what `channel_add_policy` value it carries. There is no contradiction: the publish side now matches verified reality; the consume side already matched the previously-resolved research decision, which was about event *kind*, not content.

- **P2.4 heuristic decision (2026-08-02):** research.md Q2 left the exact reply-loop heuristic (time-window vs. reply-chain/event-tag based) as an implementation-time decision. Chose **per-channel consecutive-agent-message count within a time window** (5 messages / 30s, `buzzLoopGuardMaxConsecutiveAgent`/`buzzLoopGuardWindow` in `internal/adapter/gateway/buzz/loop_guard.go`) over a reply-chain/event-tag approach. Reason: Buzz's `kind:9` channel messages carry no reliable "in-reply-to" event tag for this gateway to follow (channel messages are flat, `#h`-scoped posts, not threaded via an `e`-tag reply reference in the schema this gateway builds/consumes) — a chain-following heuristic would have nothing dependable to chain on. A consecutive-count-within-window is a direct, easily-reasoned-about bound: any human message resets the streak (so legitimate human-in-the-loop exchanges are unaffected regardless of length), and the streak ages out after `window` so occasional, spaced-out agent traffic in a channel never falsely accumulates toward the threshold. Verified by test at both the `loopGuard` unit level (`loop_guard_test.go`) and the `Gateway.processEvent` integration level (`gateway_test.go`'s `TestGateway_ProcessEvent_RunawayAgentChain_Terminates`/`_SingleAgentReply_NotSuppressed`/`_HumanToAgentExchange_NotSuppressed`).
- **P2.3 kind:9000 tag shape (2026-08-02):** verified directly against `github.com/block/buzz`'s `crates/buzz-relay/src/handlers/side_effects.rs` (`handle_put_user`): a kind:9000 event carries a required `#h` channel tag, a required `p` tag naming the target member pubkey, and an *optional* `role` tag. Critically, an absent `role` tag means "no role change requested" — the relay preserves the member's existing role rather than defaulting it — so `handleMembershipEvent` in `gateway.go` intentionally does nothing (does not clear/reset the cache) when the `role` tag is absent, matching the relay's own semantics rather than assuming a role-tag-less event means "not a bot."
- **P2.3 generalized dedupe/verify (2026-08-02):** Phase 1's `processEvent` only ever handled `kind:9`. Extending it to also process `kind:9000`/`kind:10100` meant deciding whether those kinds get the same dedupe-by-ID + signature-verification treatment. Chose yes, uniformly, for all kinds this gateway acts on — an unverified kind:9000 could otherwise let any client claim (falsely) that a pubkey has `MemberRole::Bot` via a spoofed event, corrupting `agentCache` and, downstream, the loop-prevention guard's leniency toward "known agents." `processEvent` was restructured so dedupe/verify run once, generically, before a `switch` on `Kind` dispatches to `handleAgentStatusEvent` (9000/10100) or `processChannelMessage` (9) — this is a real hardening beyond what Phase 1 needed, not a no-op refactor.
- **P2.1 (2026-08-02):** `nostr.Client` had no publish path in Phase 1 (read-only). Added relay connection tracking (`relayConn{conn, writeMu}`, `connsMu`/`conns map[string]*relayConn`, populated by `runConnection` around the existing dial/subscribe sequence) and `Client.Publish(ctx, Event) (int, error)`, which writes an `["EVENT", event]` frame to every currently-connected relay and succeeds if at least one relay accepts the write (mirrors Phase 1's partial-connectivity NFR for reads). Gave `Event` NIP-01 wire JSON tags (`id`/`pubkey`/`created_at`/`kind`/`tags`/`content`/`sig`) so it marshals directly into the outgoing frame — previously only manually unmarshaled on the read path, never marshaled. `Gateway.Send()` builds a `kind:9` event with the required `#h` tag from `OutgoingMessage.Metadata["channel_id"]`, signs it via the existing `nostr.Sign`, and publishes it, incrementing `buzz_events_published_total{status}`.

## Edge Cases & Solutions

- **go.mod `go` directive bump (1.24.0 → 1.25):** `github.com/btcsuite/btcd/btcec/v2` v2.5.0's own go.mod requires `go 1.25`; `go mod tidy` bumped our directive accordingly and dropped the explicit `toolchain go1.24.13` pin (the installed go1.26.0 toolchain already satisfies `go 1.25`). This is a real, necessary consequence of the P0.1 dependency choice, not an incidental side effect — left as-is.
- **`EnsureBuzzKeypair` typed against `domain.CredentialVault`, not `*crypto.VersionedVault`:** data-dictionary.md/tasks.md P1.6b describe persistence "through the existing `VersionedVault`," but `VersionedVault` is not actually wired into `main.go` anywhere (`app.Vault` is a `*crypto.FileCredentialVault`, which is already AES-256-GCM per `aes.go` — the property the spec actually cares about). Typing the helper against the `domain.CredentialVault` interface (which both implementations satisfy) keeps it usable with whatever vault `main.go` actually constructs, without a broader, out-of-scope change to also wire `VersionedVault` in.
- **Pre-existing, unrelated bug found during manual `./bin/nuimanbot --help` verification:** on a completely fresh checkout (no `.env`), the auto-generated encryption key is base64-encoded (`crypto.SaveEncryptionKeyToEnv`) but consumed as raw bytes at `cmd/nuimanbot/main.go:144` (`crypto.NewFileCredentialVault(vaultPath, []byte(cfg.Security.EncryptionKey))`), so vault creation fails with "encryption key must be 32 bytes for AES-256" on true first run. Confirmed via code reading that this exists on `main` independent of any Buzz change (untouched code paths: `ensureEncryptionKey`, `SaveEncryptionKeyToEnv`, `NewFileCredentialVault`, line 144). Not fixed — out of Phase 0+1 Buzz scope; flagging for a separate fix. Verification of Buzz wiring itself was done by supplying a valid raw 32-byte `NUIMANBOT_ENCRYPTION_KEY` directly.
- **`golangci-lint` cache flake:** a stale-cache run briefly reported an SA5011 nil-pointer finding in an untouched file (`internal/infrastructure/crypto/extra_test.go`) after adding new files to the same package; `golangci-lint cache clean` resolved it to 0 issues. Confirmed pre-existing/unrelated via `git diff --stat` showing no changes to that file.

## Deviations from Plan

- Added `internal/infrastructure/storage/file_user_repository.go` (`FileUserRepository`, implementing `usecase/user.ExtendedUserRepository`) — not listed in spec.md's Scope of Changes. Required because no production `domain.UserRepository` implementation existed anywhere in the codebase (only a test mock in `usecase/user/service_test.go`); without it, P1.8/P1.9's RBAC user-resolution wiring into `main.go` would have been unreachable/theoretical. Stores `domain.User` (RBAC identity) at `./data/domain_users.json`, distinct from the pre-existing `./data/users.json` (`domain.UserProfile`, a different schema used by the admin/web-UI profile subsystem) to avoid a file-format collision. See Technical Decisions above.

## Lessons Learned

- NIP-01's canonical ID-computation serialization must be hand-rolled, not built with `encoding/json`: Go's JSON marshaler escapes additional characters (`<`, `>`, `&`, U+2028, U+2029) beyond NIP-01's mandated seven, which would silently produce wrong event IDs relative to other Nostr clients for content containing those characters. Verified against an independently-computed (Python `hashlib`/`json`) reference vector, not just internal self-consistency.
- When a spec's research questions assume a fact not yet verified against the actual upstream source (here: that Buzz has a per-message agent-identity tag), it's better to go read the real source (`github.com/block/buzz`, via `gh api`/raw file fetch) than to trust a plausible-sounding assumption carried over from the PRD — the real answer (membership-role-based, not tag-based) changed how `sender_is_agent` needed to be scoped for Phase 1.
