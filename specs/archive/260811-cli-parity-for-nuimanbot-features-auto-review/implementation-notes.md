**Created:** 2026-08-11

**Purpose:** Record decisions made during implementation, edge cases encountered, and lessons learned. Update this file as each workstream/task progresses — do not wait until the end of the pass. Cross-reference the relevant task ID from `tasks.md` (e.g. "A.1", "B.2") for each entry.

## Technical Decisions

### A.1 (FR-002) — Research Question 1: Chat-context ownership failure mode

**Decision: hard rejection for BOTH ContextTypeChat and ContextTypeProject** — not the soft-fail/best-effort pattern Project previously used.

Rationale, established from primary source before writing any code:
- `FileProjectRepository`'s own doc comment (`internal/infrastructure/storage/file_project_repository.go:20-24`) states cross-owner access "naturally resolves to ErrNotFound without any extra ownership check" — i.e. `GetProject(ownerUserID, projectID)` deliberately cannot distinguish "belongs to someone else" from "never existed." This is a stated anti-IDOR/existence-oracle defense, not an oversight.
- The Chat-ownership path (`chats.Service.GetChat`, mirrored by the new `chatOwnershipCheckAdapter`) has the identical property, implemented differently: `ConversationRepository.GetConversation(convID)` fetches by ID alone, then the usecase layer compares `.UserID` and returns `domain.ErrNotFound` on mismatch — so "not owned" and "doesn't exist" are externally indistinguishable there too.
- Given that, the PRD's literal ask ("distinguish 'not owned' from 'stale/deleted, owned'") is unsatisfiable at `CreateJob` time without re-introducing an existence oracle — which would itself be a regression. The only safe, spec-compliant resolution is: any `contextID` that fails to resolve to an entity owned by `ownerUserID` is rejected, full stop, for both context types. This also directly satisfies spec.md line 157's literal requirement ("never silently attaches to another user's Project/Chat") more strongly than a partial/soft-fail fix would have.
- This does **not** regress Edge Case #2 (the original "stale Project reference" tolerance test). Edge Case #2's actual protection is about a Project deleted *after* a Job was created referencing it — `CreateJob`-time validation cannot observe a future deletion regardless of how it's written. That protection is unaffected: it lives in `internal/infrastructure/scheduler/stub_executor.go`'s `checkProjectExists` (`errProjectDeleted`), which still runs at execution time. Only the *creation-time* tolerance for an already-unresolvable reference was removed — and that tolerance was never actually distinguishable from the cross-owner bug FR-002 exists to close, so nothing meaningful is lost. Renamed the affected test from `TestCreateJob_StaleProjectReferenceStillCreatesJob` to `TestCreateJob_UnresolvedProjectReferenceIsRejected` to reflect this, with a doc comment cross-referencing both the old name (for searchability) and `stub_executor.go`.

**Sub-decision: nil-tolerance asymmetry between `ProjectDirectoryLookup` and `ChatOwnershipCheck`.**
- `ProjectDirectoryLookup` keeps its pre-existing nil-tolerance (a nil lookup skips verification, `WorkingDirectory` stays unresolved) — this is a real, tested, pre-existing contract (`TestCreateJob_NilProjectLookupStillCreatesJob`) that predates FR-002 and isn't itself the bug being fixed.
- `ChatOwnershipCheck` is a **brand-new** interface introduced by this fix. It has no pre-existing contract to preserve, so it fails closed instead: a nil `chatOwnership` with a non-empty `--chat` contextID rejects `CreateJob` rather than silently skipping verification. Rationale: nil-tolerance on a freshly-introduced security check would let a future caller who forgets to wire it silently reopen the exact hole this fix closes, with no test able to catch the omission. Production always wires a non-nil `chatOwnershipCheckAdapter` (`cmd/nuimanbot/extended_context.go`).
- The `default:` branch of `verifyContextOwnership`'s switch (an unrecognized/empty `ContextType` paired with a non-empty `contextID` — unreachable via any current caller, since `job_commands.go`'s `parseContextFlag` and `jobs_handler.go`'s `handleJobCreate` both only ever pair a non-empty contextID with a matching `ContextTypeProject`/`ContextTypeChat`) also fails closed, for the same reason — consistency, and defense against a future caller introducing a third context type without updating this switch.

### A.1 (FR-002) — Research Question 5: test-harness approach

**Decision:** `TestGetJob_CrossOwnerIsolation`'s pattern (create as one owner, assert cross-owner access fails) was directly reusable for `CreateJob`'s test, but required first upgrading `service_test.go`'s `fakeProjectLookup` from a single-level `map[string]string` (projectID -> dir) to an owner-scoped `map[string]map[string]string` (ownerUserID -> projectID -> dir), matching `job_commands_test.go`'s pre-existing `stubProjectLookup` shape. The single-level fake could not represent "project exists, but for a different owner" at all — it could only represent "exists" or "doesn't exist" — so it was structurally incapable of exercising the cross-owner case this fix needed to prove. Added `fakeChatOwnership` (same owner-scoped shape) for the new Chat-context tests.

### A.1 (FR-002) — Research Question 4 (StubExecutor's eventual replacement): partially discharged

Added a doc-comment obligation directly on `StubExecutor` (`internal/infrastructure/scheduler/stub_executor.go`) flagging that a future content-reading executor must re-verify Chat-context ownership at run time before reading Chat content, since `CreateJob`-time verification cannot protect against ownership changing (or being bypassed via a different creation path) between Job creation and eventual execution. No separate tracked FR/issue was filed for the stub's eventual replacement itself (that's a larger, unscoped future feature) — the doc comment exists so the obligation isn't lost when that replacement happens, which is what this research question actually asked for.

### A.1 (FR-002) — cross-adapter effect (discovered during self-review, not in the original task scope)

`jobs.Service` is shared between the CLI and web adapters by design (`cmd/nuimanbot/extended_context.go`'s `wireExtendedContextEnvironments` passes the same `*jobs.Service` instance to both `webServer.SetJobsService` and the CLI gateway wiring). Because the fix is in the usecase layer, **`internal/adapter/web/jobs_handler.go`'s `handleJobCreate` is also affected**: a `project_id` form value that doesn't resolve to a Project owned by the logged-in web user now causes `CreateJob` to return `domain.ErrNotFound` instead of silently creating a Job with an unresolved `WorkingDirectory`. This is correct and desirable — the web form was exposed to the identical bug (a tampered `project_id` field), just outside this review PRD's stated diff scope (which was scoped to the CLI-parity branch's changes) — but it is a real behavior change to a component this pass wasn't tasked with touching, so it's recorded here for visibility.

One rough edge intentionally NOT fixed in this pass (out of scope for FR-2, which is about `CreateJob`'s usecase-layer behavior, not the web adapter's error-code mapping): `handleJobCreate` only special-cases `domain.ErrInvalidInput` as HTTP 400; the new `domain.ErrNotFound` case falls through to `Error500` (500 Internal Server Error) rather than a more accurate 400/404. Verified via `internal/adapter/web/jobs_handler_test.go`: its tests are wired against a `MockJobsService`, not the real `*jobs.Service`, so no existing web test exercises this path or was broken by this change — but no test proves the new error path is handled gracefully either. Flagging as a follow-up-worthy nit, not fixing here to keep this fix's diff scoped to what FR-2 actually requires.

### A.1 (FR-002) — Refactor phase (mandatory per AGENTS.md)

### B.1 (FR-001) — truncation approach

- `memoriesBrowseDisplayLimit` is defined as `= historyListDisplayLimit` (a direct alias, not an independently-chosen number) so `/memories browse` matches `/history list`'s cap *exactly*, per the review PRD's explicit instruction not to invent a different threshold. If `historyListDisplayLimit` ever changes, `/memories browse`'s cap changes with it automatically — intentional, not an oversight.
- **Deviation from data-dictionary.md:** data-dictionary.md's Value Objects section states `memoryv2.MemoryCellFilter`'s existing `Limit` field "must actually be set by `browse()` for FR-001." It is deliberately NOT set on the `ListCells` call. Reason: `browse()` applies a client-side, case-insensitive substring query filter (`filterCellsByQuery`) *after* fetching cells — `memoryv2.MemoryCellFilter` has no free-text query field to push that filtering down to the repository layer. Setting `Limit` at the `ListCells` call would cap the *pre-filter* result set, producing an incorrect "Found N" count and a wrong "more not shown" trailer whenever a query narrows the results (e.g. only 3 of the first `Limit`-capped cells might match a query that has 30 matches further down the unfetched tail). Instead, `browse()` fetches the full owner-scoped set, applies the query filter, then caps for *display* only — exactly mirroring `/history list`'s own shape (its `--job`/`--chore`/`--status`/`--since` filters run at the repository layer via `domain.RunFilter`, but its `historyListDisplayLimit` display cap is still applied client-side afterward, not via a repository-level limit). This is the "match the established pattern," not a deviation from it, even though it deviates from data-dictionary.md's specific implementation guess.
- Per the review PRD's own "Optional / non-blocking follow-up" for FR-1 (sort-order parity with `internal/adapter/web/memories_handler.go`'s `sortCellsByCreatedAtDesc`): deliberately NOT implemented in this pass — the PRD explicitly marks it non-gating ("does not gate this finding's completion"), and it's unrelated to the unbounded-output bug FR-1 actually requires fixing.
- Did NOT add separate per-cell `Content` truncation beyond the count cap: `memoryv2.MaxContentLength` already bounds each cell to 2000 chars at the domain layer, and `/history show`'s `historyContentPreviewLimit` (4000) is calibrated for run logs/results, an unrelated and much larger data shape — reusing it here would never actually trigger and inventing a new sub-2000 threshold for cell content specifically would be exactly the "different scheme" the review PRD said not to invent. The count cap (20 cells, matching `/history list`) is what actually bounds output size.

### B.2 (FR-003) — deferred chat subcommand messages

- Four new unexported message constants, one per handler file, following the naming convention `data-dictionary.md` anticipated: `projectChatNotImplementedMessage` (project_commands.go), `jobChatNotImplementedMessage` (job_commands.go), `choreChatNotImplementedMessage` (chore_commands.go), `historyChatNotImplementedMessage` (history_commands.go).
- Message format: `'/X chat' is not yet implemented (deferred, see spec.md FR-0NN). Use '/X help' for available commands.` — follows the PRD's own suggested wording (FR-3's Acceptance Criteria example) and matches Settings' existing convention (`retentionSetNotImplementedMessage`, `networkModeNotImplementedMessage`).
- Each handler's `switch` gained a dedicated `case "chat":` returning its constant, placed before the `default:` fallthrough (which still handles genuine typos/unrecognized subcommands unchanged). The four `default:`-case doc comments that previously explained "falling through to this response is deliberate, guards against building new CLI-only chat capability" were rewritten in place (not deleted) to describe the new `case "chat":` location instead — the underlying rationale (don't build real chat capability) is unchanged, only where it's implemented.
- **Test-package asymmetry (deliberate, not an inconsistency):** `project_commands_test.go` and `chore_commands_test.go` are `package cli` (white-box), so their tests assert exact equality against the unexported constants directly. `job_commands_test.go` and `history_commands_test.go` are `package cli_test` (black-box) and cannot reference those unexported constants, so their tests instead assert on distinctive, stable substrings (the quoted command, "not yet implemented", and the FR number) — still "the specific message text" per tasks.md B.2's acceptance criteria, not merely "some non-crashing response." The constants were deliberately kept unexported (matching Settings' existing convention) rather than exported to paper over this asymmetry.
- Each of the four also gained a "bare `/X chat` with no further args" test case, since a user typing just `/project chat` to discover what it does is exactly the scenario FR-003 exists for — confirmed it does not fall through to `showHelp()` (which is what a `< 2`-token input would otherwise trigger).

## Edge Cases & Solutions

- A.1: `TestCreateJob_StaleProjectReferenceStillCreatesJob` ("Edge Case #2" in the original feature) turned out to encode a requirement that is unsatisfiable in the literal form the PRD described (see Technical Decisions above — "not owned" and "stale/deleted" are provably indistinguishable at the repository layer, by design). Resolved by hard-rejecting both cases identically and confirming, via `stub_executor.go`'s `checkProjectExists`, that Edge Case #2's actual run-time protection (a Project deleted *after* Job creation) is unaffected. Test renamed to `TestCreateJob_UnresolvedProjectReferenceIsRejected`.
- A.1: `ContextTypeChat` had zero existing tolerance tests before this fix (no "stale/deleted" precedent to preserve, unlike Project) — resolved by giving it hard-rejection from the start, with no soft-fail transition period, since there was no existing behavior to be backward-compatible with.

## Deviations from Plan

- **A.1 (FR-002):** `data-dictionary.md` anticipated "possibly a new sentinel error type... e.g. `ErrContextNotOwned`... to let the CLI layer produce an accurate message." Decided against this: introducing a distinguishing sentinel error would itself leak whether a contextID exists-but-is-foreign vs. never-existed — exactly the existence-oracle the repository layer's design deliberately avoids. Instead, `CreateJob` returns `domain.ErrNotFound` (wrapped with a generic, non-disclosing message), consistent with the existing codebase-wide convention for cross-owner access (`GetJob`, `GetProject`, `GetChat` all do the same).
- **A.1 (FR-002):** `tasks.md`'s acceptance criteria say the fix must "distinguish 'not owned' from the already-handled 'stale/deleted, owned' case." As established above, this is not achievable without an existence oracle; the fix instead treats both as the same rejection. See Technical Decisions above for the full argument. This is the one place this pass's task breakdown needed a substantive correction, not just an open-question resolution.

## Lessons Learned

- A PRD acceptance criterion can encode an assumption that turns out to be architecturally impossible to satisfy literally (FR-002's "distinguish 'not owned' from 'stale/deleted'") without the underlying design actually being wrong — in this case the repository layer's inability to distinguish them was a deliberate anti-IDOR choice, not a bug. Worth checking a repository/lookup's own doc comments for stated design intent before assuming a acceptance criterion's literal wording is achievable; the fix ended up stronger (hard-reject both) than the literal ask (distinguish then soft-fail one case) would have been.
- Self-review via `advisor` after each individual fix (per the PRD's binding Fix Process Guidance) caught real issues before they compounded: A.1's fail-open `default:` branch and the undocumented web-adapter cross-effect; A.1's missing `documentation/` update, only surfaced and paid off during C.1 (several tasks later — a reminder that "update docs in the same commit" can slip past self-review at the time of the original change and still needs to be caught before the pass is called done, not just checked once per task); B.2's test-package white-box/black-box asymmetry; C.1's phantom "ADR-020 Optional follow-up" cross-reference that didn't actually exist in the file. None of these would have been caught by the quality-gate chain alone (`go vet`/`golangci-lint`/`go test` all stayed green throughout) — they were documentation-accuracy and design-consistency issues, not compile/test failures.
- `jobs.Service` being shared between the CLI and web adapters (by this feature's own architectural design, `wireExtendedContextEnvironments`) means a usecase-layer fix scoped to "the CLI's new entry point" (FR-002's stated framing) silently also changes web behavior. Worth checking "what else calls this service" before treating a usecase-layer fix as adapter-scoped, even when the review PRD frames it that way.
- `specs/` being gitignored except `specs/archive/` makes "file a separately tracked issue" ambiguous by default — a new spec subdirectory looks like tracking but isn't durable for anyone but the current checkout. Confirming `gh issue`/`gh repo` work before committing to a tracking mechanism (rather than assuming a spec directory suffices) avoided producing a FR-005 "fix" that would have silently failed its own acceptance criterion.
