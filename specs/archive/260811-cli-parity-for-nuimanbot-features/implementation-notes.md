# Implementation Notes: CLI Parity for NuimanBot Features

**Feature:** cli-parity-for-nuimanbot-features
**Created:** 2026-08-11

## Purpose

Running log of decisions, edge cases, and deviations discovered during implementation, not anticipated at spec/planning time. Update this file as implementation proceeds — do not wait until the end.

## Technical Decisions

Implementation has not started; the entries below are from pipeline Step 2 (`dev-flow:review-spec`), which found and resolved several gaps by reading the actual current code rather than relying solely on the PRD's description of it. See `architecture.md` for the full decisions (AD-1 through AD-6).

- **AD-1's type-alias draft was rejected and replaced with a wrapper struct.** The original draft (`type AuthService = auth.Service`) does not compile against `internal/adapter/web/auth_coverage_test.go`'s white-box tests (which call unexported methods and read an unexported field directly) or two production call sites. Verified by reading the actual test file and `auth.go`'s `handleLogin`, not assumed. See `architecture.md` AD-1.
- **AD-2's "re-derive Role at restore time" recommendation was correctness-motivated, not security-motivated, and the original phrasing conflated the two.** Re-deriving `Role` from the live user store fixes a legitimate staleness case (demoted admin) but does not defend against a malicious local user forging their own session file's `username` field. The actual security resolution is a decided threat-model statement (OS-user-account trust boundary), not a validation trick. See `architecture.md` AD-2.

## Edge Cases & Solutions

- A CLI-restored session (AD-2) whose persisted `role` no longer matches the current value in the underlying user store (e.g. an admin demoted between CLI sessions) — resolved: `RestoreSession` re-derives `Role` from the live user store at restore time, and independently re-validates `ExpiresAt` and `Username`-existence (fail closed on either). See `architecture.md` AD-2 for the full reasoning, including what this does and does not defend against.
- `/memories` vs `/memory` prefix dispatch ambiguity — resolved and verified, not just recommended: `IsMemoryCommand`'s existing `strings.HasPrefix(input, "/memory ")` (note trailing space) already does not collide with `/memories ...` (7th character differs, `'y'` vs `'i'`). The new `/memories` dispatch needs the same discipline plus a bare-`/memories`-with-no-args test. See `architecture.md`'s Integration Points section.
- **New, found during Step 2 review — a second identity-bridge gap in the RBAC engine, distinct from FR-R7:** `internal/usecase/chat/service.go`'s `defaultRoleForPlatform(PlatformCLI) = RoleAdmin` auto-provisions a `domain.User` with admin RBAC privileges for any never-before-seen CLI `platformUID`. Once FR-007 replaces the hardcoded `"cli_user"` literal with `session.Username`, every distinct logged-in username becomes a "never-before-seen platformUID" on their first chat message, and would get auto-granted `RoleAdmin` regardless of their real `auth.Service` role — unless the login flow reconciles `domain.User`'s role first. Resolved as AD-6 in `architecture.md`; task P2.3 in `tasks.md`.
- **New, found during Step 2 review — `ownerUserID` convention.** All six existing web handlers pass `session.Username` (not `session.ID`/`domain.User.ID`) as `ownerUserID` into `internal/usecase/{chats,projects,jobs,chores,history,memories}`. The CLI must match this exactly or CLI-created and web-created data silently diverge into separate owner namespaces. Resolved as AD-5 in `architecture.md`; documented in `data-dictionary.md`.
- **New, found during Step 2 review — `/job create --project <id>` for a Project the logged-in user doesn't own.** Traced `internal/usecase/jobs/service.go`'s `ProjectDirectoryLookup.OutputDirectoryFor(ctx, ownerUserID, projectID)` — scoped by the *caller-supplied* `ownerUserID`, which the CLI handler always sets to the logged-in user (never attacker-controlled), so a foreign `projectID` naturally resolves to not-found. Safe by construction as long as the CLI handler never accepts a `--user`-style override (no FR proposes one). Still needs an explicit acceptance test (added to `spec.md`'s acceptance criteria and `tasks.md` P3.3) rather than relying on the underlying scoping being correct without verification.

## Deviations from Plan

- **Found during Phase C/D implementation — FR-043's `/settings set network-mode` has no shared state to mutate, and this PRD's own Open Questions already anticipated exactly this doubt.** `domain.NetworkAccessConfig` is owned entirely as private state inside `*web.Server` (`internal/adapter/web/middleware.go`'s `networkAccessState`), with no usecase-layer holder the CLI can reach without importing `internal/adapter/web` (forbidden — hard acceptance criterion). Flagged to the pipeline coordinator with three options (small extraction to share state; defer; CLI-local-only setting); decision (received, not self-directed): **Option 2, defer**, because even a successful extraction wouldn't make the setting functionally effective — FR-R11 (a known, pre-existing, deliberately-deferred gap from the six-environments feature) means even the web UI's own network-mode control doesn't rebind the running listener. Extracting shared state now would be most of the way to a setting that *looks* like it does something but doesn't, one architectural layer removed — not worth the unplanned refactor across `web/middleware.go`, `web/server.go`, `settings.Service`, and `main.go` wiring until FR-R11 itself is fixed. `/settings show --system` and `/settings set network-mode` both surface a clear "deferred, see FR-R11" message rather than silently no-op'ing; `/settings set worker-pool-size` (fully backed) proceeds as specified. See `spec.md` FR-041/043 for the corrected text.
- **Found during Phase C/D implementation — FR-039/040's "per-user retention" has no backing capability, same class of gap as the four deferred chat sub-commands, but not caught during Step 2's review.** Verified `internal/domain/preferences.go`'s `UserPreferences` (the only per-user settings store that exists) has zero retention fields, and `internal/adapter/web/settings_handler.go`'s `SettingsService` interface doc comment states outright that per-user retention override storage is deferred (system-wide/admin-only today; `RetentionPolicy` is fixed per-resource at creation time from a single system-wide default). Flagged to the pipeline coordinator mid-implementation rather than guessing; decision (received, not self-directed): defer FR-040 and FR-039's per-user "set" half, same DEFERRED treatment as FR-020/026/031/036. `/settings show` instead displays the system-wide retention default read-only, mirroring what the web UI's Settings page actually shows today. `/settings set worker-pool-size`/`set network-mode` (FR-041-043, system-wide/admin-only) are unaffected — real backing exists, proceed as specified. See `spec.md` FR-039/040 for the corrected text.
- **Scope reduction, not a plan deviation per se, but load-bearing:** FR-020 (`/project chat`), FR-026 (`/job chat`), FR-031 (`/chore chat`), and FR-036's chat half (`/history chat`) are deferred, not implemented. Verified against the actual merged web code that none of the four corresponding `*Service` interfaces (`ProjectsService`, `JobsService`, `ChoresService`, `HistoryService`) has a chat/converse method — three of the four handler files have explicit "out of scope for this pass" comments already in the codebase (`jobs_handler.go:155`, `chores_handler.go:102`, `history_handler.go:230`). Building these as CLI-only new capability would itself violate the PRD's Non-Goal against introducing new product surface. See `spec.md`'s Non-Goals and the corresponding FR entries, `architecture.md`'s "Scope correction" section.
- **Acceptance-criteria package-path correction:** the PRD's (and the original spec.md draft's) acceptance-criteria bullet referenced `internal/adapter/cli` — an unrelated, pre-existing package (`internal/adapter/cli/{memory,persona,skill}.go`) with no auth/login concerns at all. The package this feature actually modifies is `internal/adapter/gateway/cli`. As originally written, the acceptance criterion was trivially, meaninglessly true (the unrelated package obviously never imports `internal/adapter/web`) and would not have caught a real Clean Architecture violation. Corrected in `spec.md`. The PRD file itself (`cli-parity-for-nuimanbot-features-PRD.md`) is left as-is, being the immutable source record; this note documents the deviation for traceability. Confirmed via `find`/`grep` that today, neither `internal/adapter/cli` nor `internal/adapter/gateway/cli` imports `internal/adapter/web` — no pre-existing violation to fix as part of Phase A.

## Lessons Learned

- Reading the actual current code (not just the PRD's summary of it) surfaced six concrete issues the PRD/spec-creation pass missed or got subtly wrong: a non-compiling type-alias design, a mischaracterized security fix, a second independent auto-admin shortcut in a different subsystem, an ownerUserID convention with no compile-time enforcement if violated, a wrong package path in a hard acceptance criterion, and three FRs with no backing implementation to mirror. None of these were visible from spec.md/architecture.md's text alone — all required grepping and reading the actual `.go` files and their test files. Recommendation for future specs in this pipeline: Step 1 (spec creation) or Step 2 (review) should always include a code-verification pass proportional to how much the spec claims to "mirror" or "reuse" existing behavior — the higher that claim's weight, the more it needs checking against the literal code, not just the web UI's FR list.
