# Data Dictionary: CLI Parity for NuimanBot Features

**Feature:** cli-parity-for-nuimanbot-features
**Created:** 2026-08-11

## Purpose

Defines the data structures, types, and schemas this feature introduces or reuses, spanning the new `internal/usecase/auth` service and the new CLI command handlers. Populated progressively as `architecture.md` and implementation proceed.

## Entities

- **`domain.User`** (existing, `internal/domain`) — `ID string`, `Username string`, `Role domain.Role` (a distinct string-based type: `RoleGuest`/`RoleUser`/`RoleAdmin`, with `.Level()`/`.HasPermission()`), `PlatformIDs map[Platform]string`, `AllowedTools []string`, `CreatedAt`/`UpdatedAt`. Used by the pre-existing `internal/usecase/chat` engine's RBAC (`resolveUser`/`GetUserByPlatformUID`), keyed by `PlatformIDs[PlatformCLI]`. **This is a separate identity system from `AuthUser`/`Session` below** — see "Two identity systems" note under Interfaces.
- **`AuthUser`** (moves from `internal/adapter/web/auth.go` to `internal/usecase/auth`, unchanged fields) — `Username string`, `PasswordHash string`, `Role string` (plain string, not `domain.Role` — no change made to this during the extraction; conversion needed at the CLI boundary, see below).
- **`Session`** (moves from `internal/adapter/web/auth.go` to `internal/usecase/auth`, unchanged fields) — `ID string`, `Username string`, `Role string`, `CreatedAt time.Time`, `ExpiresAt time.Time`, `ForcePasswordChange bool`. No `Source`/`Platform` discriminator added — not needed; the CLI adapter is the only thing that persists sessions to disk, so nothing needs to distinguish a CLI-origin session from a web-origin one at the `auth.Service` layer.
- **`Role` type mismatch, CLI boundary conversion required:** `Session.Role` is a plain `string` (e.g. `"admin"`). `domain.User.Role` is `domain.Role` (`type Role string`, with `RoleAdmin = "admin"` etc.). When the CLI constructs `&domain.User{Role: ...}` for `Gateway.SetCurrentUser` (or when AD-6's identity-reconciliation step compares roles), it must explicitly convert: `domain.Role(session.Role)`. The underlying string values already line up (`auth.Service`'s roles are the same lowercase strings as `domain.Role`'s constants) but the compiler requires the explicit conversion — flag this in the implementing PR's code review checklist so it isn't silently done as a raw string-to-string field copy that happens to compile because both are strings.
- **CLI Session Token File** (new) — on-disk JSON, permissions `0600`, located alongside the existing `HistoryFile` path convention (`internal/config/gateway_config.go`'s `CLIConfig.HistoryFile`). Schema: `{"session_id": string, "username": string, "role": string, "created_at": RFC3339 string, "expires_at": RFC3339 string}` — mirrors `auth.Session`'s fields exactly (all exported, straightforward `json.Marshal`/`Unmarshal`). No `ForcePasswordChange` field needed on disk — the CLI doesn't implement forced-default-credential-change UX (out of this PRD's scope; only the web admin's default-credentials flow needs it).

## Value Objects

- **`ownerUserID` (not a new type — a calling convention, confirmed by grep across all six existing web handlers):** every call from `internal/adapter/web` into `internal/usecase/{chats,projects,jobs,chores,history,memories}` passes `user.Username` (the authenticated session's `Username` field) as the `ownerUserID` parameter — never `user.ID`/`session.ID`. `internal/adapter/web/projects_handler.go`'s doc comment states this explicitly: *"ownerUserID is the current session's Username ... session.ID is a per-session token, not a stable user identifier."* **The CLI adapter must follow the identical convention**: every new environment handler passes `session.Username` as `ownerUserID`. This is architecture.md's AD-5. Getting this wrong produces no compile error and no runtime error — it silently creates CLI-only records invisible to the web UI (and vice versa), which only an acceptance test comparing CLI- and web-visible data would catch.
- Command-argument parse results for the new `/chat`, `/project`, `/job`, `/chore`, `/history`, `/memories`, `/settings` commands — one small parsed-args struct per subcommand, following whatever pattern existing admin command handlers use (see `internal/adapter/gateway/cli/admin_commands.go` for the existing convention to mirror). No new shared value-object type needed beyond what each handler defines locally.

## Interfaces

- **`internal/usecase/auth.Service` surface** (new, finalized per `architecture.md` AD-1) — exported: `NewService() *Service`, `AddUser(username, password, role string) error`, `ValidateCredentials(username, password string) bool`, `GetUser(username string) (AuthUser, bool)` (**new** — replaces `web/auth.go`'s old direct `s.auth.users[username]` field access, which cannot survive the package move), `CreateSession(username, role string) string`, `CreateSessionWithFlags(username, role string, forcePasswordChange bool) string` (**now exported** — was `createSessionWithFlags`; `web`'s wrapper still exposes it under the old lowercase name via a shim, see architecture.md AD-1), `ValidateSession(sessionID string) bool`, `GetSession(sessionID string) *Session`, `DestroySession(sessionID string)`, `ClearForcePasswordChange(sessionID string)`, `UpdatePassword(username, newPassword string) error`, `IsDefaultCredentials(username, password string) bool` (**now exported**, same reasoning as `CreateSessionWithFlags`), `RestoreSession(session *Session) error` (**new**, AD-2 — independently re-validates `ExpiresAt` and that `Username` still exists in the live `users` map before re-hydrating into the in-memory `sessions` map; returns an error on either failure, which the CLI adapter treats identically to "no valid session file"). **Not exported / stays internal to `internal/usecase/auth`:** `sessions map[string]*Session`, `users map[string]*AuthUser`, `csrfTokens` (doesn't move at all — stays in `web`), `generateRandomString`, `runCleanupLoop`/`cleanupExpiredSessions`.
- **`internal/adapter/web.AuthService`** (wrapper struct, not a type alias — see architecture.md AD-1) — embeds `*auth.Service`; own fields `csrfTokens map[string]bool`, `secureCookies bool`, `mu sync.RWMutex` (guards only the wrapper's own fields). `NewAuthService()` stays zero-arg. Unexported shim methods `setSecureCookies`/`isSecureCookies`/`createSessionWithFlags`/`isDefaultCredentials` are declared directly on this wrapper (in package `web`) so existing lowercase-named test call sites keep compiling.
- **`cli.New*Handler` constructors** (new, one per implemented environment: Chats, Projects, Jobs, Chores, History, Memories, Settings) — follow the existing `cli.NewSkillHandler` / `AdminBotCommandHandler` pattern; each wraps the corresponding `internal/usecase/*` service. Per `architecture.md`'s "Scope correction," Projects/Jobs/Chores/History handlers expose only list/show/create/delete(/confirm-schedule); no chat sub-command (deferred, see spec.md FR-020/026/031/036).
- **`Gateway.Set*Handler` methods** (new, one per environment) — follow the existing `SetAdminHandler`/`SetProfileHandler`/`SetBotHandler`/`SetMemoryHandler`/`SetConfigHandler`/`SetSkillHandler` pattern in `internal/adapter/gateway/cli/gateway.go`.
- **Two identity systems, not one — a fact this feature must reconcile, not just consume (architecture.md AD-6):**
  1. **`auth.Service`'s `AuthUser`/`Session`** — the login-gate identity: a small, admin-managed set of `{Username, PasswordHash, Role}` accounts, used purely to decide "is this REPL session authenticated, and as whom." This is what FR-001/002/006 operate on.
  2. **`domain.User`/`UserRepository`** (via `internal/usecase/user`'s `userService`, and consumed by `internal/usecase/chat.Service.resolveUser`) — the RBAC/tool-execution identity: a `PlatformIDs`-keyed record, auto-created on first message per `(platform, platformUID)` pair via `defaultRoleForPlatform`, which **hardcodes `RoleAdmin` for `PlatformCLI`** (comment: *"CLI is inherently local/trusted ... preserves the CLI's pre-existing de facto unrestricted access"* — written under the old, now-being-replaced, no-real-login assumption). This governs actual tool-execution permission during any agent chat (the plain-text REPL chat FR-007 targets, and — once built — any future per-item chat sub-command).
  These two systems are not currently linked. Without AD-6's reconciliation step, a real `RoleUser` login via system (1) would still get system (2)'s auto-provisioned `RoleAdmin` on first chat message, silently defeating FR-006.

## Enumerations

- **`domain.Role`** (existing, `internal/domain/user.go`) — `RoleGuest = "guest"`, `RoleUser = "user"`, `RoleAdmin = "admin"`; reused unchanged for CLI command gating (FR-006). Note: `auth.Service`'s `AuthUser.Role`/`Session.Role` are plain `string`, not this type — see the Role type-mismatch note under Entities.
- **Settings retention scope** — `chat | project | history` (FR-040), plus a `never` value.
- **Network access mode** — `localhost | remote` (FR-043, admin-only, inherits pre-existing web limitation).

## API Request/Response Types

N/A at the transport level — this feature has no HTTP API surface; the CLI is a terminal REPL. The "request/response" shapes are command-line argument tuples in and formatted terminal text out, consuming the existing `internal/usecase/*` method signatures already used by the web adapter (no new usecase-layer request/response types expected — reuse what the web handlers already call, always with `ownerUserID = session.Username` per AD-5).

## Status

Finalized during pipeline Step 2 review against the actual code (not left as architecture-phase TBD): `auth.Service`'s method surface, the session-file JSON schema, the `ownerUserID`/`Username` convention, and the `Session.Role`/`domain.Role` conversion point are all resolved above. Per-subcommand argument-parsing structs for the seven new command families are intentionally left to implementation time (Phase C/D in `plan.md`) — they're mechanical, low-risk, and follow an existing in-repo pattern (`admin_commands.go`), not an open design question.
