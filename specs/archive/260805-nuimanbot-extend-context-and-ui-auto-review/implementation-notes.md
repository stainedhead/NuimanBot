# Implementation Notes: NuimanBot Extend Context & UI — Auto-Review Fix Pass

**Created:** 2026-08-05

## Purpose

This file records decisions, edge cases, and lessons learned during implementation of the 19-finding fix pass. Update it continuously as work proceeds — do not wait until the end. In particular, this fix pass has **four Open Questions with stated defaults** (see `research.md`) that must have their actual resolution recorded here, explicitly, as each relevant finding is closed. The PRD itself flags that a prior instance of exactly this kind of silent, undocumented deferral decision (Chats' agent-invocation gap, FR-R1) was the real problem it found — not the deferral itself, but the fact it wasn't written down. Do not repeat that here.

## Technical Decisions

*(To be filled in during implementation. Record the actual choice made for each of the following, with rationale, as soon as it's decided — not retroactively.)*

- FR-R5: **Decided.** `domain.ConfinedFileStore` (EnsureDir/WriteFile/FileExists/Confine — Confine added by FR-R18, see below), implemented by `internal/infrastructure/storage.FileConfinedFileStore`. `jobs.Service`/`chores.Service`/`projects.Service` all take it as a constructor param; a single shared instance is wired in `cmd/nuimanbot/extended_context.go`. Regression: `layering_test.go` in each of the three packages parses `service.go`'s own imports and fails on `os`/fsguard.
- FR-R6: **Decided.** Centralized in `fsguard.go` as a new function, `ResolveWithinNoEscape` (plus `MustBeWithinNoEscape` for FR-R18's different call shape — both share a private `verifyNoEscape` walker), not `filepath.EvalSymlinks` inlined at each call site. Walks the resolved path component-by-component, resolving symlinks at each existing step; a not-yet-existing component is treated as literal (can't be a symlink) so the function is safe to call before creating a new file — the ENOENT trap the PRD's execution guidance flagged. Wired into `FileConfinedFileStore` (WriteFile/FileExists/Confine), `FileProjectRepository.recordPath`, and `StubExecutor.writeResults`. Left on plain `ResolveWithin`: Job/Chore/Run record-path resolution — not because the ID is validated, but because the only writer into those directories is that repository's own Save method, always naming files via `uuid.NewString()`, so nothing can plant a symlink there for a resolution to stumble into (confirmed by second-reviewer pass, see below).
- FR-R18: **Decided.** No existing `internal/config` "projects root" value was found; used the stated default, `<storagePath>/users/<ownerUserID>/projects/`, via a new `allowedRootBase` constructor param on `projects.Service` (wired from `app.StoragePath`). `CreateProject` validates `outputDirectory` against this per-owner root via the new `domain.ConfinedFileStore.Confine` method (backed by `fsguard.MustBeWithinNoEscape`) before any directory is created. **Route-gating judgment call:** the PRD's finding text describes `/admin/projects` being `RoleUser`-gated (not admin-only) as part of why the unconfined directory was severe ("any authenticated user can reach this"), but its acceptance criteria only requires the confinement fix, and spec.md's own FR-017 ("User can create a Project") + FR-010 ("full isolation, including from admins") make clear Project creation is deliberately ordinary per-user self-service, not an admin-only operation. Changing the route to `RoleAdmin` would have broken the feature FR-017 describes. **Decision: left `/admin/projects` at `RoleUser`, unchanged** — the fix is confining the destination, not restricting who may create a Project. Documented directly in `CreateProject`'s doc comment too, and flagged explicitly to the second-reviewer pass for this specific judgment call.
- FR-R1: **Decided (Workstream D).** Documented deferral, not implementation — the PRD's own Non-Goals section states "Wiring the *live* Chats reply loop (FR-R1, via full `internal/usecase/chat` multi-turn/tool/RBAC orchestration)... [is a] separately-scoped follow-up effort, not a target of this pass." `chat_detail.html` now carries a visible amber notice above the message form: "Automatic replies are not yet available for Chats — your message is saved, but the agent will not respond here yet." — the gap is disclosed, not silent, satisfying the finding's actual acceptance criteria ("either a working reply loop, or an explicit, non-silent documented deferral + UI notice").
- FR-R4: **Decided (Workstream D).** Memory is the reference implementation. Rationale: Job already had an existing (if inert) "Chat interface coming soon." placeholder to preserve as the "not yet available" pattern for the other three; Memory's content (a single bounded text field) is the simplest possible grounding context for a minimal single-turn template; and choosing Memory kept this workstream's files (`memories_handler.go`, `memory_detail.html`, `memories/service.go`) fully disjoint from Workstream E's Job/Chore/History detail-template edits, avoiding a merge collision in this shared (non-worktree-isolated) working directory. Implementation: `memories.Service.AskAboutCell(ctx, ownerUserID, cellID, question)` — ownership enforced by delegating to the existing `GetCell` before any LLM call; a new `memories.LLMService` interface (just `Complete`, structurally satisfied by `domain.LLMService` — no adapter needed) issues one grounded completion per question via a `SystemPrompt` built from the cell's Scene/Type/Salience/Content, deliberately NOT `internal/usecase/chat.Service`'s full multi-turn/tool-calling/RBAC orchestration engine (that integration is FR-R1, out of scope). New route `POST /admin/memories/{id}/ask` (CSRF-protected) renders the answer inline on the same detail page — no persisted per-item conversation history, an explicit minimal-template scope choice recorded here rather than left implicit. Job/Chore/Run detail pages all now say "Chat interface coming soon." (Chore/Run added to match Job's pre-existing notice) rather than omitting the affordance, per the finding's requirement that the deferred three must not be silent either. Wired in `cmd/nuimanbot/extended_context.go` via `memories.WithLLM(app.LLMService)`/`WithLLMDefaults` sharing `cfg.LLM.DefaultModel` with `chat.Service`.
- FR-R11: **Decided (Workstream F).** UI-honesty-only, no live listener rebind — per `research.md` Q3's stated default. The POST handler's `network_mode` branch is unchanged (it already had a genuine, if partial, live effect on the allowlist-check middleware). The fix is entirely in `settings.html`: Bind address is now rendered as a disabled `<input>` labeled "(config file only)" (previously not rendered at all, despite `SettingsPageData.NetworkBindAddress` existing since the original implementation); the Allowlist block gained the same "(config file only)" label; and a new note under the Network access mode `<select>` clarifies that changing it only affects the allowlist-check middleware's behavior for connections that already reach the process — it does not rebind the actual listener, which is fixed at process start. A live listener rebind (accepting an admin-submitted bind address/allowlist and restarting the HTTP server) remains explicitly out of scope, consistent with the PRD's own default.
- FR-R7: **Decided (Workstream D).** Confirmed (no longer merely assumed) via `TestFR_R7_ConversationIDMapping_TracesRealCLIGatewayFormat` (`internal/usecase/memories/conversation_id_mapping_test.go`), which creates a memory cell through the real curator path (`memoryv2.MemoryCuratorService.ExtractCells`, real file-backed repositories) using the exact literal ConversationID format the production CLI gateway emits: `"cli:cli_user"` (`internal/adapter/gateway/cli/gateway.go` hardcodes `PlatformUID: "cli_user"` for every CLI message — not even user-specific yet). This is `chat.Service.getConversationID(platform, platformUID) = platform + ":" + platformUID`, never the web-admin session Username `memories.Service` receives as `ownerUserID`. Further confirmed: `internal/adapter/web`'s login/session code never references `domain.UserRepository`/`domain.User` at all — the web-admin account system and the domain.User/gateway-platform-identity system are two entirely separate, unbridged identity spaces in this codebase today, so even a lookup-based fix has no existing table to join through. **No real mapping was implemented** — building one (plus fixing the CLI gateway's own single-shared-placeholder identity, a prerequisite for the mapping to mean anything) is a separately-scoped identity-unification effort, out of this pass for the same reason as FR-R1. Instead: the package doc comment in `memories/service.go` was rewritten from "ASSUMPTION, needs reviewer confirmation" to the confirmed, evidenced finding with the full citation trail; `memories.html` carries a visible notice that the view may not show everything. This satisfies the acceptance criteria's actual text ("trace... what ConversationID value memory cells actually carry... end-to-end" + "add an integration test... not just the synthetic fixture") without pretending a deeper architectural gap was closed.
- FR-R14: **Decided (Workstream F): removed**, not wired in. `grep -rn "IsQueueable"` confirmed zero non-test callers. Considered wiring it into `jobs.Service.CreateJob`'s enqueue path, but `CreateJob` is the *only* place that ever enqueues a Run for a Job, and it always constructs a brand-new `domain.Job{Status: JobStatusQueued, ...}` — freshly created, never `PendingDeletion`, so `IsQueueable()` would always return `true` there and the call would be a no-op guard with no real case it could ever reject. There is no re-run/retry/re-enqueue flow anywhere in the codebase today for an *existing* Job (with a real, possibly-Running/Queued/PendingDeletion Status) to need this check against. Rather than wire in a guard that can never actually fire, removed `IsQueueable()` from `internal/domain/job.go` and deleted `job_test.go` (its 4 dedicated tests were its only contents). The decision and a pointer for future reintroduction ("wire it into whatever enqueue call a re-run/retry flow adds, guarding that flow specifically") is recorded as a code comment in `internal/usecase/jobs/service.go`, next to `DeleteJob`'s existing `PendingDeletion`-sweep-integration TODO — the two are related (both about what happens to a Job across its create/delete/re-run lifecycle) so keeping them adjacent is more discoverable than a comment on the deleted method itself.

- FR-R19 (Workstream E): centralized into `baseDataFor` (the shared "build BaseData for an authenticated request" path, per the finding's own preferred approach in `tasks.md`) rather than per-handler duplication. `baseDataFor` gained a `ctx context.Context` first param (16 call sites updated); `withUnviewedRunCount` gained a `historyService == nil` guard since it's now reachable from every environment, not just History's own two handlers that had already null-checked it for other reasons. `dashboard_handler.go`'s `getDashboardData` was also switched from calling `NewBaseData` directly to `baseDataFor`, folding Dashboard into the same shared path (it was the one page bypassing it entirely).
- FR-R10 (Workstream E): plain vanilla JS (`internal/adapter/web/static/run-events.js`), no framework/build step — connects directly to the existing `/ws` endpoint and `RunEvent` wire shape, no new backend surface needed. Job/Chore pages identify their event stream via `data-source-type`/`data-source-id` on `<body>` (matched against `RunEvent.SourceType`/`SourceID`, since these pages don't track their current Run's ID); Run detail matches directly via `data-run-id`. `nav.html`'s notification badge `<span>` changed from a `{{if}}`-gated conditional element to an always-rendered element toggled with a `hidden` CSS class, so the script has a stable `#notification-badge` node to update in place. See Deviations from Plan for the manual-verification gap and the `_js`-filename Go build-constraint gotcha hit while adding the test.
- FR-R2 (Workstream A): re-enqueue-vs-fail decision for a Run reconciled at startup — **always Failed, never re-enqueued.** No live Executor exists yet with known idempotency guarantees (StubExecutor is a stub), so re-enqueuing could silently duplicate or lose partial side effects; failing with a clear `Error = "run interrupted by server restart"` is the only choice that can't do that. `domain.RunRepository` gained `ListAllNonTerminal` (cross-user, mirroring `ChoreRepository.ListAllDue`'s precedent) for the startup scan. Wired in `cmd/nuimanbot/extended_context.go` between `queue.Load()` and `pool.Start(ctx)`.
- FR-R3 (Workstream A): sweep loop is `internal/infrastructure/scheduler.RetentionSweeper`, same ticker-poll-loop pattern as `ChoreScheduler`, polling every 15 minutes (`defaultRetentionSweepInterval`). Per-user iteration via a new `domain.UserProfileRepository.ListProfiles`-backed `UserLister` interface — retention is a system-wide default (Settings/FR-003), not yet per-user configurable, so the same three policies apply to every user.
- FR-R9 (Workstream A): combined into `RetentionSweeper`'s same per-user loop rather than a second ticker (per the task's own guidance), via a new `Cleaner` interface (`CleanupPendingDeletion(ctx, ownerUserID) (int, error)`) both `jobs.Service` and `chores.Service` now implement. Both reuse an internal `hasActiveRun` check against `RunRepository` (not `Job.Status`/`Chore` fields) — notably, `Job.Status` is never actually kept in sync with its Run's lifecycle anywhere in this codebase (no caller invokes `JobRepository.UpdateStatus`), so deriving activeness from the Run record directly, as Chore already had to (it has no Status field at all), is the only reliable signal for both.

## Edge Cases & Solutions

*(To be filled in during implementation.)*

- Edge Case #7 (retention sweep deleting an unviewed Run must decrement the notification badge, never reference a deleted Run) — **resolved, already held before FR-R19 and unaffected by it.** FR-R3's `RetentionSweeper`/`history.Service.SweepExpired` deletes Run records outright (not just marks them read); `UnviewedCount`/FR-R19's `withUnviewedRunCount` derive the badge count fresh from `RunRepository` on every call (there is no separate cached counter that could go stale or reference a deleted Run) — a swept Run simply stops contributing to the count on the next page render, by construction, not by any special-cased interaction code. FR-R19's only change is *where* that fresh count gets read (every authenticated page instead of just History), which doesn't alter this property. Covered transitively by the existing `TestRetentionSweep_...` integration tests (Workstream A) plus `TestNotificationBadge_AppearsOnNonHistoryPages` (Workstream E) — no combined test was added since the two code paths don't actually interact beyond both reading the same repository.
- Edge Case #2 (Job/Chore run against a deleted Project) — record the exact failure path implemented for FR-R12.
- Edge Case #3 (deleting a Job/Chore while its run is active) — **resolved.** FR-R8 (Chore soft-delete) landed first per the spec's own sequencing; FR-R9's `CleanupPendingDeletion` then assumed and built directly on that — a Chore already soft-marks `PendingDeletion` exactly like Job, so both entities' cleanup sweep logic is structurally identical (list all, filter `PendingDeletion`, check `hasActiveRun`, hard-delete if clear). Verified via `TestRetentionSweep_CleansUpPendingDeletionJobsAndChores`, a real-repository integration test exercising both through the actual sweep loop, not just each Service's own unit test.

## Deviations from Plan

*(To be filled in during implementation. This section is where the four Open Questions' actual resolutions get recorded — mandatory, per the Purpose note above.)*

- **FR-R17 second-look (post-completion verification, not a change):** `FileRunRepository.ReadResults` (Workstream G) reads `Run.ResultsPath` via raw `os.ReadFile`, not re-resolved through `fsguard` at read time — worth double-checking given this same pass just hardened symlink-escape handling (FR-R6). Verified this is not a regression: `grep -rn "\.ResultsPath\s*=" internal --include="*.go"` (excluding tests) shows exactly one production writer, `StubExecutor.writeResults`, which computes the path via `fsguard.ResolveWithinNoEscape(runDir, "RESULTS.md")` — a hardcoded literal filename, not derived from any request input — under `<storagePath>/scheduler/runs`, an internal executor-only artifact root no Job/Chore/Project write path can reach (unlike Project output directories, which FR-R6/FR-R18 harden specifically because agents/users *can* write there). Same reasoning already accepted elsewhere in this pass for Job/Chore/Run record-path resolution (see FR-R6's entry above: "the only writer into those directories is that repository's own Save method... so nothing can plant a symlink there"). No code change made; recorded here so this isn't silently unexamined.
- **FR-R10 (manual/live-browser verification not performed):** the acceptance criteria calls for "manually verified (or browser-level test if tooling exists) that starting a Run and watching its detail page shows status transition and log growth live." No browser is available in this environment, so this was not done. What was verified instead: `TestRunEventsJS_ServedAndWiredIntoDetailPages` (`internal/adapter/web/run_events_client_test.go`) proves `/static/run-events.js` is served, contains real `new WebSocket(...)` client code and all three documented event-type strings (`run_status`/`run_log`/`notification_badge`), and that each of Job/Chore/Run detail pages includes the script tag plus every DOM anchor (`#job-status`/`#chore-status`/`#run-status`/`#run-log`, `data-source-type`/`data-source-id`/`data-run-id`) the script depends on. The existing `TestHandleWebSocket_UpgradesAndReceivesPublishedEvent` (pre-existing, Hub-level) independently proves the server-side publish path delivers a `RunEvent` to a real WebSocket connection. Together these cover everything short of an actual browser executing the JS against a live page — recorded here rather than silently claiming full verification.
- **FR-R7 (not a deviation from the PRD's stated acceptance criteria — the acceptance criteria's own "trace it, test it" is the resolution mechanism, and both were done — but a real residual gap worth tracking explicitly):** the `ownerUserID` -> `ConversationID` mismatch is now proven, not merely assumed, and is NOT closed. A real fix needs two separately-scoped pieces of work this pass did not attempt: (1) a genuine identity bridge between the web-admin account system (`internal/adapter/web/auth.go`, entirely disconnected from `domain.User` today) and the gateway-identity system (`domain.User.PlatformIDs`); (2) fixing the CLI gateway's own hardcoded single-shared `PlatformUID: "cli_user"` placeholder so CLI interactions are even attributable to a real per-operator identity in the first place — without (2), (1) alone wouldn't help CLI-sourced memories. Also orphaned from Workstream D itself (see the Progress Summary correction in `tasks.md`): FR-R7 was in the source PRD but never assigned to any workstream in the original 7-workstream table, discovered and added as Task D.3 mid-pass.
- **FR-R18 follow-up (not a deviation from the PRD's stated acceptance criteria, but a real residual gap a second-reviewer pass found and this note tracks explicitly rather than leaving silent):** `CreateProject`'s allowed-root confinement is a create-time check. `AddAgentsFile` now re-validates `p.OutputDirectory` against the owner's allowed root on every call (added same day, same commit as the fix), since FR-022 grants the user direct filesystem access to a Project's OutputDirectory and nothing prevents an on-disk component along that path from being replaced with a symlink after creation. **Not yet closed:** Job/Chore run execution (`jobs.Service.CreateJob`'s `WorkingDirectory` resolution via `ProjectDirectoryLookup.OutputDirectoryFor`, and whatever `Executor` ultimately reads/writes against it) still trusts the persisted `OutputDirectory` without an equivalent re-check. Closing that fully requires either threading the same allowed-root convention into `jobs`/`chores` (a `ProjectDirectoryLookup` implementation choice, not a `projects.Service` change) or re-validating at `Executor` dispatch time. Deferred past this fix pass — out of FR-R18's stated acceptance criteria (which only requires confining `CreateProject`'s input), but flagged here per this PRD's own lesson about not leaving a deferral undocumented.
