  - **P7.1 (path-traversal hardening) — real vulnerability found and fixed:** Verifying "adversarial tests exist for Job/Chore file ops, not just the fsguard unit" surfaced that `FileJobRepository`/`FileChoreRepository`/`FileProjectRepository`/`FileRunRepository` all built their record (and, for Run, log) paths with raw `filepath.Join(userDir, id+".json")` — never routed through `fsguard.ResolveWithin`, despite fsguard's own package doc explicitly mandating this. Verified exploitable in isolation (a crafted ID like `"../../../../etc/passwd"` read an arbitrary file off disk and returned it as a valid record) before fixing. The current web handlers happened not to expose this today only incidentally (net/http's ServeMux redirects literal `".."` segments away before routing; each handler's path-parsing only ever extracts a single non-slash segment as the ID) — not a deliberate control, so this was a real defense-in-depth gap, not a confirmed live HTTP exploit. **Fixed** by routing all four repositories' `recordPath`/`logPath` through `fsguard.ResolveWithin`, mapping any resolution failure uniformly to `domain.ErrNotFound` (never disclosing more than "not accessible to you", consistent with the codebase's existing IDOR posture). Added adversarial tests per repository: a table of traversal strings against Get/Delete(/AppendLog for Run), plus a concrete plant-bob's-record/craft-alice's-ID cross-owner scenario for each. fsguard's own unit itself already had adversarial tests from Phase 2 (unaffected, still passing) — this closes the gap between "the helper is safe" and "every call site actually uses it." **Follow-up item deliberately not fixed this pass:** `FileConversationRepository` (pre-existing, backs Chats, predates this feature) has the identical raw-`filepath.Join(userDir, convID+...)` pattern on `convID` — same shape of gap, left alone as out of scope for this feature's hardening pass, but worth a dedicated follow-up.
